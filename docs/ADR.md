# Architecture decisions

These decisions record choices that would materially change the app if reversed. Coding rules
are in [AGENTS.md](../AGENTS.md); calculation assumptions are in [methodology.md](methodology.md).

| ID      | Date       | Status                | Decision                                                                                                                                                                                                                                          | Rationale and consequences                                                                                                                                                                                                                                                                                                   |
| ------- | ---------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ADR-001 | 2026-11-25 | Accepted; implemented | Build the site as a single pre-rendered static HTML file (`dist/index.html`) with inlined CSS and vanilla progressive-enhancement JavaScript, zero frontend frameworks, zero bundled web fonts, and hash-based strict CSP (`connect-src 'none'`). | Price cap data is static and changes quarterly. Pre-rendering HTML and inlining CSS and minimal JS (~10 kB gzipped total) delivers the complete interactive app in a single HTTP round trip, eliminates asset cache skew across deploys, and keeps the core dashboard and 14-region table readable with JavaScript disabled. |
| ADR-002 | 2026-11-25 | Accepted; implemented | Use Temporal (`temporal-polyfill`) as the date and time model across domain, build, parser, and test code; use `Intl.DateTimeFormat` (`Europe/London`) with exact `BigInt` Gregorian civil-day arithmetic for the tiny client-side countdown.     | Cap period boundaries follow UK civil calendar dates (`Europe/London`), so Temporal avoids host-timezone assumptions and JavaScript `Date` quirks. Keeping `temporal-polyfill` out of the client bundle preserves the ~10 kB single-file payload while still avoiding JavaScript `Date` and floating-point arithmetic.       |
| ADR-003 | 2026-11-25 | Accepted; implemented | Use `decimal.js-light` for all numeric arithmetic throughout the domain, build-time renderer, tests, and Ofgem parser tooling.                                                                                                                    | Binary floating-point rounding can shift pence per kWh and standing charge rates by 0.01p. Values stay as `Decimal` through calculations and SVG chart geometry, rounding explicitly at display and serialisation boundaries.                                                                                                |
| ADR-004 | 2026-11-25 | Accepted; implemented | Refresh `data/price-cap.json` directly from Ofgem's official Annex 9 workbook via GitHub Actions and trigger GitHub Pages redeploys only when data changes, plus on quarterly rollover dates (1 Jan, 1 Apr, 1 Jul, 1 Oct).                        | Eliminates third-party data mirrors and avoids wasted daily rebuilds while ensuring new Ofgem announcements and quarterly status flips deploy automatically without manual steps.                                                                                                                                            |
